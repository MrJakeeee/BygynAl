# BugunAL

Первый этап сервиса продажи излишков еды в Бишкеке: регистрация, авторизация и профиль трёх ролей. Бэкенд — отдельное Spring Boot API в корне проекта, фронтенд — отдельное приложение в `frontend/`. Обмен только JSON по `/api`. PostgreSQL, Flyway, Spring Security, BCrypt. Java 17+, Maven, Node.js 20+.

## Запуск

1. Скопируйте `.env.example` в `.env`, заполните свои значения. Файл исключён из Git.
2. Создайте PostgreSQL-базу `bugunal` и пользователя `bugunal` с паролем из `DB_PASSWORD`. Либо выполните `docker compose up -d postgres`, если установлен Docker. Миграции запускаются автоматически. Существующие чужие базы не изменяются.
3. Для отправки через Gmail задайте `SMTP_USERNAME` и **пароль приложения Google** в `SMTP_PASSWORD`. У Google-аккаунта должна быть включена двухэтапная проверка и доступна возможность создания пароля приложения. Обычный пароль аккаунта сюда не подходит. SMTP по умолчанию: `smtp.gmail.com:587`, STARTTLS.
4. Запустите бэкенд из корня: `powershell -ExecutionPolicy Bypass -File scripts/start-backend.ps1`. Он загрузит `.env` в окружение процесса. Без скрипта задайте переменные через конфигурацию запуска IntelliJ и запустите `BygynAlApplication`, либо используйте `mvn spring-boot:run` / `./mvnw.cmd spring-boot:run`. Сам Spring Boot автоматически `.env` не читает.
5. В другом терминале: `cd frontend`, затем `npm run dev`. Установка npm-зависимостей не нужна. Откройте **http://localhost:5173**. Бэкенд слушает порт 8080. Фронтенд проксирует API на него; приложение не использует `file://`.

`ADMIN_EMAIL` и `ADMIN_PASSWORD` создают первого администратора при первом запуске. Пароль — от 12 символов, буквы и цифры; при первом входе требуется смена. Существующий пароль не перезаписывается. После создания удалите эти две переменные из `.env`. Сотрудника можно создать из кабинета администратора: сначала заведение, затем сотрудник. Временный пароль приходит сотруднику на Gmail; до его смены рабочие API закрыты.

Без действующих PostgreSQL и SMTP реальную регистрацию пройти нельзя. Приложение не возвращает коды в API и не печатает их в журнал.

## Реализованные сценарии

- Покупатель вводит имя, Gmail, телефон и пароль. Код приходит на почту; только после его проверки создаётся учётная запись. После регистрации требуется обычный вход.
- Пароль: минимум 8 символов, буквы и цифры, максимум 72 байта UTF-8 для BCrypt. Регистр Gmail игнорируется; точки в локальной части нормализуются, чтобы один почтовый ящик не создавал несколько аккаунтов. Поддерживаются адреса `@gmail.com`, без `+`-псевдонимов.
- Вход по Gmail и паролю. Пять последовательных ошибок блокируют вход на 15 минут. Блокировка администратором завершает все сессии на следующем обращении к API.
- Двухфакторную проверку можно включить или выключить в профиле: текущий пароль + код на Gmail. Если 2FA включена, сессия входа создаётся только после второго фактора.
- Восстановление: код на Gmail, одноразовый, срок 30 минут. Новый пароль завершает старые сессии; включённая 2FA сохраняется.
- Коды регистрации, входа и изменений профиля действуют 10 минут. Для каждого кода допускается пять попыток; повторная отправка — через 60 секунд, предыдущий код аннулируется. Коды генерируются `SecureRandom`, в базе хранится BCrypt-хеш.
- Профиль: изменение имени и телефона, смена пароля, подтверждённая смена Gmail. Изменения безопасности завершают существующие сессии.
- Администратор: поиск пользователей, блокировка и разблокировка, создание заведения и сотрудника с обязательной привязкой. Самоблокировка запрещена. Действия записываются в `admin_audit` и журнал приложения.

## Соответствие ТЗ

Требования прочитаны из `ТЗ_BugunAL_v1.1.docx`; текстовая копия — `requirements.txt`. Для этого этапа использованы пункты 3.1–3.3, 4.1, 4.2.1–4.2.2, 4.15.1–4.15.2 в части учётных записей, 4.15.7, 5.3 и 6.6. Полный каталог, заказы, платежи, статистика и редактирование сведений о заведении относятся к следующим этапам и здесь не реализованы. Запрос покупателя не позволяет выбрать роль продавца или администратора.

По прямому указанию заказчика изменены положения ТЗ: серверные Thymeleaf-страницы заменены отдельным фронтендом и REST API; восстановление по ссылке заменено кодом с тем же сроком 30 минут. Добавлены подтверждение регистрации через Gmail и добровольная 2FA через Gmail. Стек Java 17, Spring Boot **3.4.13** (ветка 3.4 из ТЗ), JPA, PostgreSQL, Flyway, Spring Mail и BCrypt сохранён. Макеты Google Stitch не были предоставлены; текущий адаптивный интерфейс является самостоятельным оформлением.

## Безопасность и развёртывание

Аутентификация использует серверную сессию и HttpOnly-cookie. Все изменяющие запросы, включая вход и регистрацию, требуют CSRF-токен. GET `/api/auth/csrf` возвращает токен и имя заголовка; клиент передаёт его в каждом POST/PATCH. Идентификатор сессии меняется при входе. Роли проверяются сервером. Сохранение контекста сессии выполнено явно согласно [документации Spring Security](https://docs.spring.io/spring-security/reference/6.5/servlet/authentication/persistence.html).

Для production используйте HTTPS, `COOKIE_SECURE=true`, один публичный домен с прокси `/api` к бэкенду и правильный `FRONTEND_ORIGIN`. Node-сервер из `frontend/server.mjs` предназначен для локальной разработки. Пароли, SMTP-ключи и содержимое писем не должны попадать в репозиторий. Сессии сейчас хранятся в памяти одного экземпляра бэкенда и завершаются при его перезапуске; БД хранит пользователей и запросы подтверждения. Перед публичным размещением настройте ограничение запросов на reverse proxy и резервное копирование PostgreSQL с хранением 30 дней, как требует ТЗ.

## Проверка

`mvn test` — интеграционные тесты API с H2 в режиме PostgreSQL и подменённым SMTP: регистрация и повтор кода, лимиты, истечение кодов, вход, 2FA, сброс пароля, завершение сессий, роли, CSRF и сбой отправки письма. Это не проверка доставки реальных писем и не замена проверки на PostgreSQL.

`cd frontend; npm run check` — проверка синтаксиса JavaScript.

В текущем ограниченном окружении Maven не может скачать Spring Boot 3.4.13 из Maven Central. Результат дополнительных локальных проверок записывается в `VERIFICATION.md`. Для проверки доставки выполните регистрацию на своём Gmail после настройки SMTP.
